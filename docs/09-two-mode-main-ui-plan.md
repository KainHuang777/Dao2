# M2-D 雙狀態主介面規劃（Godot 已實作，Web／觸控待驗收）

日期：2026-09-25。這是依使用者提出的兩種常態情境制定的版型契約；`living_abode.gd`、`building_catalog.gd` 和響應式 Runner 已依此修改。下文「現況」保留改版前問題描述。Godot CLI 通過不等於 Web 畫面、滑鼠或觸控驗收通過；當次需求優先於本文件。

最新操作入口（2026-09-25）：底部常駐「空島／營造」雙分頁，預設空島，點營造即開右側建築簿，點空島返回。資源在左側 HUD 下方以「關閉／數量／完整」切換；預設數量。下文舊版「頂部／建築欄內資源」尺寸與成本常駐建議已由 [新版規格](07-responsive-ui-web-spec.md) 取代；建築列統一 48 高，費用只在點列展開後顯示。

## 目標與現況

優先情境只有兩個：A「看空島、境界與少量資源，操作底部主按鈕」；B「常態同時看資源與建築」。建築詳情、系統訊息全文、存檔、九界與輪迴都是從這兩個狀態進出的暫態，不應各佔一塊永久浮動面板。

現行 `living_abode.gd` 寬式未開清單時有約 `380×210` HUD、`260×56` 縮放列、`660×104` 系統訊息與 `460×64` 底部導航。開清單時再加入最寬 `540×600` 清單、右側 HUD／訊息／詳情，並隱藏導航。`building_catalog.gd` 把資源、採集、建築放在同一個 ScrollContainer；捲到後面的建築，資源便離開視野。`844×390` 開清單時，左右欄之間約只剩 87px，不能把它當成仍可操作空島的版型。這些是程式推算與現有截圖觀察，不是新方案的實機量測。

## 共同最小資訊與點擊預算

以下是設計起點，單位為 Godot 邏輯像素；`44×44 CSS px` 是實際 Web 驗收下限，兩者不可直接視為相等。

| 元件 | 常態最低可見資訊 | 建議視覺預算 | 操作命中預算 |
| --- | --- | --- | --- |
| 境界 HUD | 境界與層數、修煉進度、剩餘壽元；重要晉階／突破動作在符合條件時顯現 | 桌面寬 280–320、高 80–112；直式全寬、高 72–96；拿掉常駐地名與大型裝飾標題 | 資訊文字不需命中；任何晉階鍵至少 `48×48` 邏輯像素 |
| 最小資源列 | 目標相關 1–2 種資源的庫存／容量，必要時顯示每秒產率；解鎖更多時明示 `+N` | 併入 HUD 下段或貼齊同一卡片，1–2 行、高 40–64；不可再複製完整資源清單 | 展開管理與當前可手動採集動作各至少 `48×48`；不可把資訊文字假裝成小型按鈕 |
| 目標／系統訊息 | 一句可行的下一步和失敗／成功回饋；全文按需展開 | 常態併入 HUD 或管理面板的一行 32–48；事件可短暫提示，不維持獨立大卡 | 可展開時整行至少高 48；純訊息不攔截世界輸入 |
| 底部主操作 | 營造／返回空島、神識展開／歸家、更多功能 | 3 鍵單列，桌面高 48–56；直式高 52–56，寬度按可視區分配 | 每鍵至少 `48×48`；更多功能彈單每列也須達 `44×44 CSS px` |
| 縮放與自動存檔 | 縮放可由拖曳／滾輪／雙指或按需控制；自動存檔僅狀態異常需提示 | 不各佔一塊常駐大面板；縮放若保留圖示列，高 44 | 任何可見縮放鍵至少 `48×48`；存檔失敗須可察覺並可進管理 |
| 管理標題與建築列 | 固定返回／關閉、資源數值與產率、可建／等級／用途；不足成本需可辨識 | 標題 48；資源格 56–64；建築列 48–56，密集正文不低於 16 字級 | 標題操作與每個建築列至少高 48；不可沿用現行 40 高緊湊列 |
| 建築詳情 | 名稱、等級、產出／容量、成本與主要建造／升級動作 | 替換同一管理面板的建築列表區；固定返回列，正文捲動 | 返回／主要動作至少 `48×48`，可見或可明確捲達 |

目前清單的密度／收起鍵與緊湊建築列僅高 40，低於現行 `docs/07` 的約 44 CSS px 點擊要求；後續實作不得用縮字換空間，應刪重複資訊、合併容器並修測試。

## A：空島模式（預設）

```text
┌ HUD：境界／修煉／壽元／目標 ──────────────┐
│ 最小資源：當前關鍵 1–2 項    [採集] [展開] │
└──────────────────────────────────────────┘

                 可拖曳、可選建築的空島

          [營造設施] [神識／歸家] [更多功能]
```

- HUD、最小資源與單句目標視為同一資訊區，不再疊一張常駐「系統訊息」卡；長說明可從目標列展開，回饋訊息短暫顯示。完整資源數據不在空島模式複製。
- `1280×720` 的起始上限：左上資訊區約 320 寬、總高 140–168；底部操作單列最多約 360 寬、56 高。`360×640` 則讓資訊區全寬、總高約 128–160，底列 56。`844×390` 須把 HUD／資源改為橫向共用高度，不能把現行 174 高 HUD 再向下疊資源列。
- 以「無 UI 遮擋、可接收世界操作的連續矩形」驗證空島，不只驗面板本身未越界。目標：`1280×720` 至少 60% 畫面面積仍可直接操作世界；窄橫式至少保有中央連續的拖曳區。這是新驗收提案，仍須由實際島面構圖與 CSS viewport 確認。

## B：常態管理模式（資源與建築同時可看）

```text
┌ 單一管理欄：返回空島／標題／更多 ┐    空島仍可觀看／點選（寬式）
│ 境界摘要＋一句當前目標          │
│ 固定資源格：庫存／容量／產率    │
│ ─ 建築列表：獨立捲動 ──────── │
│ 可建、等級、用途、缺料提示      │
└──────────────────────────────┘
```

- 桌面 `1280×720` 管理欄從左側進入，建議寬 340–380，面板高不得超過可視區；HUD 與目標併入欄首，取消另放右側的訊息卡和詳情卡。世界右側仍留約 900px 寬，不用中央 87px 的假「世界區」設計。
- 資源區固定在建築列表上方，建築列自己捲動。資源採 2 欄、每格約 56–64 高，顯示名稱／庫存／容量／產率；可採集格須明示 `採集 +1`，整格或明確按鈕可點。依可視高度顯示目標相關資源，超出時明示 `+N` 並在同一管理欄展開，不靜默隱藏。避免兩個難以分辨的巢狀捲動區。
- 點建築不再同時新增右側大詳情：固定資源區留下，建築列表區切換為該建築詳情；固定「返回列表」恢復原列表捲動位置。狀態刷新不得使面板跳回頂端或送出重複命令。
- `844×390` 視作管理焦點，而非左右面板與空島都完整可玩的畫面；資源固定區縮為 1–2 行摘要，建築區保留可用高度。`360×640` 使用全幅管理頁，固定標題／返回約 48 高、資源區最多約 3 行、下方建築獨立捲動；進詳情時可暫收完整資源區，以保證主要操作和返回可達。更短 `360×480` 必須同樣不裁切。

## 狀態轉換與驗收

`空島 → 管理 → 建築詳情 → 管理（保留原捲動）→ 空島` 是唯一主路徑；從世界直接點茅屋可進同一詳情，不建立第二套資訊或命令。方向切換只重排，不改 GameSession、存檔、產率與選取。更多功能仍可進低特效、存檔、九界、說明、突破重播與輪迴；這些只在使用時蓋過當前模式，關閉回原狀態。

實作已同步 `docs/07` 的版型契約，並調整 `living_abode.gd`／`building_catalog.gd`，移除「清單左、HUD／訊息／詳情右」的舊常態。CLI 測試涵蓋新檔、多資源、`1280×720`、`1920×902`、`844×390`、`360×640`、`360×480`、資源固定、列表獨立捲動、詳情返回與幾何界線。實際可點矩形、文字換行視覺、手機觸控及 Web CSS viewport 仍須 AGY 實測；CLI 不能替代。

Godot 雙狀態已實作；M2-D 仍為 IN_PROGRESS。管理模式在短橫式／直式以管理操作優先，不強行同時維持完整空島互動；待實機確認此取捨與可讀性。
